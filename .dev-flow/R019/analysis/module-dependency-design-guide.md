# 模块依赖关系图 — 设计指南

> 本文档是对 xlfoundry-design skill 中"模块依赖关系图"绘制规范的经验总结，用于后续更新 skill 的指导规则。

## 一、读者视角：开发者想从图中获取什么

### 1. 改造范围 — 这次要动哪些东西？

- 哪些是新增的、哪些是改造的、哪些完全不用动
- 一眼看出工作量和影响边界
- **实现方式**：颜色区分（绿色=新增、蓝色=改造、灰色=不变）

### 2. 依赖方向 — 谁调谁？

- 箭头从调用方指向被调用方
- 改 A 模块时，顺着箭头看会影响谁；逆着箭头看我需要谁
- **实现方式**：箭头方向统一从上到下，禁止出现反向箭头

### 3. 依赖内容 — 为什么依赖？

- 箭头上的标签说明调用目的，比如 save/delete、recognize
- 帮助理解模块间的接口契约
- **实现方式**：标签精简到 1-3 个词，只写关键操作

### 4. 分层关系 — 谁在上谁在下？

- 上层调用下层，不能出现底层调上层
- 不能出现循环依赖
- **实现方式**：用 subgraph 分层，subgraph 标签体现层级语义

### 5. 不变模块的边界 — 红线在哪？

- 灰色模块是不可触碰的，箭头只能指向它，不能从它出发
- 不变模块只被依赖，不依赖别人（如果有，说明"不变"的判断有误）
- **实现方式**：灰色节点只能有入箭头，不能有出箭头（指向外部依赖的除外）

## 二、常见错误与纠正

### 错误 1：按"新增/改造/不变"分组而非按调用层次分组

**问题**：开发者更关心请求进来后数据怎么流经各模块，而不是模块属于哪个类别。

**纠正**：按调用层次从上到下排列 subgraph，用颜色区分新增/改造/不变。分组维度 = 层级，颜色 = 改造类型。

### 错误 2：配置和初始化模块占据画面

**问题**：main.py 和 config 各有 3-4 条箭头，是初始化和配置读取，不是运行时依赖。每个模块都读 config 是共识，不需要箭头表达。

**纠正**：
- `main.py`（初始化/挂载）不出现在图中
- `config`（配置读取）不出现在图中
- 在图例中用一句话说明省略原因

### 错误 3：utils / 辅助函数作为独立节点出现

**问题**：utils 通常是某个模块的内部实现细节（如 conversation_utils 是 conversation_router 的消息序列化辅助函数），不是一个独立的业务模块。把它画成独立节点会让依赖链变长，掩盖真正的模块关系。

**纠正**：
- utils 不作为独立节点出现
- 它的职责归入调用方对底层模块的直接依赖
- 在图例中说明省略原因

### 错误 4：基础设施模块放在不同层级

**问题**：`image_manager`（文件存储）和 `llm.py`（LLM API 调用）都是封装外部资源的底层服务，本质上是同一层。把它们分到不同层级会造成误导。

**纠正**：所有"封装外部资源的底层服务"归入同一基础设施层，无论新增还是已有。

### 错误 5：纯展示组件放在状态管理层

**问题**：image-preview 是纯展示组件，只接收 props 渲染，不持有也不管理状态。把它放在"状态管理层"混淆了职责。

**纠正**：纯展示组件归入 UI 组件层，只有持有状态逻辑的 Hook 才归入状态管理层。

## 三、分层标准

### 后端典型分层

| 层级 | 职责 | 典型模块 |
|------|------|---------|
| API 入口层 | 处理 HTTP 请求/响应 | router（upload_router, stream_router, conversation_router） |
| 业务层 | 定义业务流程和数据模型 | graph.py（流程编排）、schemas（数据定义） |
| 基础设施层 | 封装外部资源访问 | image_manager（文件）、recognition_provider（VLM）、llm.py（LLM API） |
| 外部依赖 | 系统边界外的服务 | 文件系统、Vision LLM API |

### 前端典型分层

| 层级 | 职责 | 典型模块 |
|------|------|---------|
| UI 组件层 | 纯展示 + 用户交互，不持有业务状态 | chat-input, message-bubble, image-preview |
| 状态管理层 | React Hook，管理状态 + 编排业务 | use-image-upload, controller |
| 服务层 | 封装通信协议（SSE、REST） | use-chat-stream |
| 基础设施层 | 通用工具函数 + 类型定义 | api-client, types |

## 四、节点筛选原则

### 应该出现的

- 处理请求的 router / 页面组件
- 核心业务编排模块（graph、controller）
- 封装外部资源的 service（image_manager、recognition_provider、llm.py）
- 被多方依赖的共享定义（schemas、types）
- 通信协议封装（use-chat-stream、api-client）

### 不应该出现的

| 类型 | 原因 | 示例 |
|------|------|------|
| 配置模块 | 每个模块都读配置，是全局共识 | config.py |
| 初始化入口 | 只在启动时执行一次，不是运行时依赖 | main.py |
| utils / 辅助函数 | 是调用方的内部实现细节 | conversation_utils |
| 框架层 | React、FastAPI 等框架能力不画入 | React.memo、Depends |

## 五、箭头设计原则

1. **方向**：统一从上到下（调用方 → 被调用方）
2. **标签**：精简到 1-3 个词，只写关键操作（`save/delete`、`recognize`、`onSend`）
3. **虚线**：用于区分特殊依赖（如数据产出关系），实线 = 运行时调用
4. **数量**：控制在 10 条以内，超过说明模块划分有问题

## 六、颜色方案

| 颜色 | 含义 | 色值 |
|------|------|------|
| 绿色 | 新增模块 | `#4CAF50` 或 `#66BB6A` |
| 蓝色 | 改造模块 | `#2196F3` 或 `#42A5F5` |
| 灰色 | 不变模块 | `#9E9E9E` 或 `#BDBDBD` |

## 七、图例与说明

每张图下方必须包含：

1. **颜色图例**：绿色=新增，蓝色=改造，灰色=不变
2. **省略说明**：哪些模块被省略了，为什么
3. **阅读方式**：从上到下 = 请求流向，箭头含义
4. **虚线语义**（如有）：虚线表示什么

## 八、Mermaid 渲染限制

subgraph 框（黄色背景块）的对齐是 Mermaid dagre 引擎的已知限制。框的位置由节点间的边决定，无法强制居中或等宽。以下方案均**无效**：

- `~~~` 不可见边：会破坏层级关系
- `direction LR` 在 subgraph 内：改善有限
- `linkStyle stroke-width:0`：隐藏了线但没改善对齐

**结论**：优先保证内容和层级关系正确，框对齐是渲染器差异（Typora / VS Code / GitHub 渲染结果不同），不在语法层面强求。

## 九、质量自检清单

- [ ] 分组维度是调用层次，不是新增/改造/不变
- [ ] config 和 main.py 不在图中
- [ ] utils / 辅助函数不在图中
- [ ] 同类基础设施在同一层
- [ ] 纯展示组件不在状态管理层
- [ ] 箭头方向全部从上到下
- [ ] 箭头数量 ≤ 10 条
- [ ] 箭头标签精简（1-3 词）
- [ ] 灰色节点没有向上的出箭头
- [ ] 图例完整（颜色 + 省略说明 + 阅读方式）
