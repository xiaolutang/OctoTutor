# 多模态图片识别

## 结论
- **要做什么**：支持用户在对话中上传图片（文件选择器 + Ctrl+V 粘贴），后端存储图片文件，识别图片内容后接入解题/检索链路
- **不做什么**：不限制为单一识别方案（OCR 或 Vision LLM），架构上抽象识别层，具体方案留给 analysis 调研
- **关键约束**：
  - 模型配置要抽象，支持后续切换 Vision 模型（GLM-4V / Qwen-VL / 其他）
  - OCR 效果好可省 Vision LLM 费用，需要调研成本/质量权衡
  - 图片存储走后端文件存储，消息中存 URL 引用
  - 支持图片+文字混合提问
  - 完整方案一次做完，不分期
- **核心场景**：拍题/截图问解题、图片+文字混合提问、公式识别
- **待确认**：
  - OCR vs Vision LLM 的具体技术选型（analysis 阶段调研）
  - 是否需要专门的数学 OCR（如 Mathpix）vs 通用 OCR
  - RAG 路径：OCR 转 text 后走现有检索 vs Vision 模型直答 vs 两者都支持
  - 图片存储方案：本地文件系统 vs 对象存储（S3/OSS）

## 关键讨论
- **成本优化思路**：用户提出如果 OCR 效果好就不用调 Vision LLM 省钱，这是架构分层的核心动机——抽象识别层，OCR 和 Vision LLM 作为可插拔实现
- **完整链路影响**：从上到下 5 层全部需要改动（前端输入 → API 传输 → 后端存储 → Graph 消息格式 → LLM 调用），工程量较大
- **双路径**：用户希望 RAG 和直答都支持，具体路由策略（用户选 vs 自动判断）待调研后决定
