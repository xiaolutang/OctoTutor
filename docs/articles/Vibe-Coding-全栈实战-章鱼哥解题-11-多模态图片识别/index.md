# Vibe Coding 全栈实战：章鱼哥解题 11｜多模态图片识别

前 10 期做完以后，章鱼哥解题支持纯文本问答：学生输入数学问题，系统检索教材、生成回答、流式输出。

但实际使用中有一个很自然的场景缺失：**拍题提问。** 学生拍一张数学题的照片，或者截图粘贴进来，系统能不能识别图片内容并解题？

这一期要做的事情就是：**从纯文本对话扩展到支持图片输入的多模态对话。**

---

## 一、要解决什么问题

学生用章鱼哥解题时，输入方式只有打字。但数学问题经常包含公式、图形、表格——这些东西打字描述很麻烦，拍照或截图是最自然的输入方式。

brainstorm 阶段拆解出来的核心需求：

```text
拍题/截图提问：上传一张数学题图片，系统识别内容后解题
图片+文字混合提问：上传图片的同时附带文字说明（"这道题的第二问怎么做"）
公式识别：图片中的数学公式能被正确识别
```

这一期不做的事：
- 不做语音输入
- 不做视频输入
- 不做图片标注/编辑

---

## 二、完整链路影响

多模态不是加一个"图片识别"接口就完了。从 brainstorm 的分析看，从上到下 5 层全部需要改动：

```text
前端输入层：文件选择器 + Ctrl+V 粘贴 + 图片预览
API 传输层：消息格式支持图片 URL 引用
后端存储层：图片文件存储 + 消息记录关联
Graph 消息层：AgentState 扩展图片字段
LLM 调用层：识别层抽象，OCR / Vision LLM 可插拔
```

## 三、技术选型

### 识别方案对比

| 方案 | 优势 | 劣势 | 适用场景 |
| --- | --- | --- | --- |
| OCR | 成本低，速度快 | 数学公式识别差 | 纯文字图片 |
| Vision LLM | 语义理解强，公式识别好 | 成本高 | 复杂题目 |
| 专门数学 OCR（Mathpix 等） | 公式识别最准确 | 额外依赖，有费用 | 公式密集场景 |

### 架构设计思路

brainstorm 阶段确定了一个关键约束：**识别层必须抽象，具体方案可插拔。**

```text
用户上传图片
→ 后端存储图片，返回 URL
→ 识别层（可插拔）：
    OCR 识别文字 → 走现有 RAG 检索链路
    Vision LLM 直接理解 → 混合图片+文字提问
→ 结果进入对话流程
```
