## 1. 敏捷开发流程的对照

传统敏捷流程：

```
产品 Redmine 新建需求
→ 研发-产品熟悉对齐需求
→ 研发方案设计
→ 方案评审
→ 编码实现
→ 自测
→ 提交测试
```

**待探讨的问题：**
- Vibe Coding 的六步流程（需求澄清 → 方案设计 → 任务拆解 → 实现执行 → 评估验证 → 文档沉淀）和传统敏捷是什么关系？
- 是不是可以说：Vibe Coding 不是发明新流程，而是把传统工程流程适配到 AI 编程场景？
- 传统流程里"人做所有环节"vs Vibe Coding 里"人和 AI 分工"——哪些环节 AI 能参与？哪些必须人来做？
- 产品对齐需求 ≈ 需求澄清，方案评审 ≈ 设计审查，自测+提交测试 ≈ 评估验证

## 2. 编程中的其他黑箱

**三方库的使用：**
- 用 React 时，你只需要知道 hooks 怎么用，不需要知道虚拟 DOM diff 算法的实现
- 用 FastAPI 时，你只需要知道怎么定义路由和依赖注入，不需要知道 ASGI 内部怎么处理
- 库的设计本身就是"暴露 API，隐藏实现"——这是有意的、被管理的黑箱

**模块设计：**
- 好的模块设计对外暴露 API，不暴露实现细节
- 使用者只需要理解接口契约，不需要理解内部逻辑
- 这和"代码黑箱"是同一个问题的两面：写代码的人在降低黑箱（通过清晰的 API），读代码的人在利用黑箱（只看 API 不看实现）

**待探讨的问题：**
- 三方库的黑箱和 AI 代码的黑箱有什么本质区别？
  - 三方库：黑箱边界清晰（API 就是边界），经过社区验证，有文档和类型定义
  - AI 代码：黑箱边界模糊，没有社区验证，文档就是 prompt
- 这能否引出一个观点：黑箱本身不可怕，可怕的是"没有管理的黑箱"？
- 传统编程用接口抽象来管理黑箱，Vibe Coding 用什么来管理？

## 3. AI 的行为特性

**对自己完成的任务评价较高（过度自信）：**
- AI 生成代码后会说"已完成实现"，但可能遗漏了边界条件
- AI 写完测试说"全部通过"，但测试可能不够覆盖
- 需要人来做独立验证，不能信任 AI 的自我评价

**长任务中的上下文焦虑：**
- 长时间运行的任务中，AI 会倾向于尽快完成，可能跳过重要步骤
- 上下文窗口有限，AI 在长对话中会"忘记"早期的约束和决策
- 这不是 AI 的"偷懒"，而是技术限制导致的行为特征

**擅长小任务，不擅长大系统设计：**
- 给 AI 一个明确的函数需求，它能快速生成高质量代码
- 让 AI 设计一个完整的系统架构，输出往往泛泛而谈或遗漏关键点
- 这直接支撑了"任务拆解"的必要性——不是因为任务大才要拆，而是因为 AI 只擅长小任务

**待探讨的问题：**
- 这三个特性是否可以形成一条逻辑线：AI 的能力边界决定了人的工作方式？
- 过度自信 → 需要评估验证
- 上下文焦虑 → 需要任务拆解
- 擅长小任务 → 需要人在大方向上做决策
- 这些特性是当前模型的限制，还是 AI 编程的固有特征？如果模型变强了，这些问题会消失吗？

## 4. 常见的智能体范式

### ReAct（推理 + 行动）

```text
思考(Thought) → 行动(Action) → 观察(Observation) → 思考 → 行动 → 观察 → ...
```

- 交替进行推理和行动：先想清楚当前该做什么，调用工具执行，观察结果，再想下一步
- 适合需要多步推理 + 外部工具的场景（搜索、计算、API 调用）
- 优点：每一步有明确的推理过程，可追溯
- 缺点：复杂任务容易走偏，因为每一步的决策只看当前状态，缺少全局视野

### Plan-and-Solve（先规划再执行）

```text
规划(Plan)：拆解任务为子步骤列表
→ 执行(Solve)：按顺序完成每个子步骤
```

- 先生成完整的执行计划，再逐步执行
- 适合复杂度高、步骤之间有依赖关系的任务
- 优点：有全局视野，不会因为单步决策失误导致整体跑偏
- 缺点：计划质量决定了执行质量；如果规划有误，执行阶段很难修正

### Reflection（反思迭代）

```text
生成(Generate) → 评估(Critique) → 修正(Revise) → 生成 → 评估 → 修正 → ...
```

- 生成结果后自我评估，发现不足后修正，反复迭代
- 适合需要高质量输出的场景（代码审查、文案优化、方案改进）
- 优点：通过多轮迭代逼近更好的结果
- 缺点：迭代次数和"好"的标准需要控制，否则会无限循环

### 与 Vibe Coding 流程的关系

| 智能体范式 | Vibe Coding 中的对应 | 谁来做 |
| --- | --- | --- |
| Plan-and-Solve | 方案设计 + 任务拆解 | 人规划，AI 执行 |
| ReAct | 实现执行（AI 逐个完成小任务） | AI |
| Reflection | 评估验证 | 人定义标准，自动化执行 |

**待探讨的问题：**
- Vibe Coding 本质上是不是一个"人驱动的 Plan-and-Solve + 自动化的 Reflection"？
- 人做规划（方案设计+任务拆解），AI 做执行（ReAct 模式完成小任务），人+评估体系做反思（评估验证）
- 为什么不让 AI 自己做 Plan-and-Solve？因为 AI 的"规划质量"目前不够可靠——它擅长执行具体步骤，不擅长判断"这个方案是否合理"
- 为什么不让 AI 自己做 Reflection？因为 AI 对自己的输出评价偏高（过度自信），自我反思不够客观
- 这引出一个核心观点：Vibe Coding 的流程设计，本质上是把智能体范式中的"规划"和"反思"两个环节交给人，把"执行"交给 AI
