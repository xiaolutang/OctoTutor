# Vibe Coding 全栈实战：章鱼哥解题 09｜AI 听不懂“它”：追问改写与长对话压缩

这一期遇到的 bug 很典型：用户追问一句"它呢？"，AI 就开始跑偏。

学生问"一次函数 y=2x+1 是什么"，AI 回答了。接着问"它的定义域怎么求"，AI 的回答就开始跑偏。

问题不在回答能力，而在链路里没人知道"它"指的是上一轮的"一次函数 y=2x+1"。

这个问题不是偶发的。拆开看有三个原因：

1. **respond 不传历史消息**：之前为了快速跑通单轮问答，`_respond` 节点只把当前问题和 RAG 检索结果拼在一起发给 LLM。上一轮聊了什么，LLM 完全不知道。

2. **追问里的代词对 RAG 检索没有意义**："它的定义域怎么求"拿去检索，向量模型不理解"它"指的是什么函数。检索出来的内容和用户想问的可能完全无关。

3. **没有 token 预算管理**：对话越来越长以后，所有历史消息都塞进 LLM 的 context window，最终会撞上上限。模型用的是 200K context window 的 glm-5.1，短对话没问题，但 30 轮以上就会出问题。

所以这一期做的事情是：**把单轮问答链路，改造成能处理多轮追问的长对话链路。** 改完之后，链路变成这样：

```text
用户追问"它的定义域怎么求"
→ summarize：检查 token 是否超预算，超了就压缩
→ rewrite：把"它的定义域"改写成"一次函数 y=2x+1 的定义域"
→ retrieve：用改写后的问题去检索
→ respond：带上历史消息和 RAG 结果回答
```

---

## 一、旧的图管线有什么问题

之前 LangGraph 的图拓扑是：

```text
START → classify → [retrieve → respond | refuse] → END
```

classify 是一个意图分类器，判断用户输入属于"教材问题"还是"无关问题"。教材问题走 retrieve → respond；无关问题走 refuse，直接回复"这个问题超出了我的范围"。

这个拓扑有两个问题。

第一个，**classify 的默认返回值是 textbook**。所有没命中规则的输入，都会被判为"教材问题"，触发 RAG 检索和 LLM 回复。结果"你好你好"、"今天天气怎么样"这类输入也会被当成教材问题处理，检索到无关内容后 LLM 被迫编造回答。

第二个，**这个拓扑不支持多轮**。没有 token 预算管理，没有追问改写，也没有历史消息传递。

---

## 二、新拓扑：线性四节点

重构后的拓扑是：

```text
START → summarize → rewrite → retrieve → respond → END
```

四个节点，纯线性，无条件分支：

| 节点 | 解决什么问题 |
| --- | --- |
| summarize | token 预算管理：超阈值时压缩对话，避免撞 context window |
| rewrite | 追问改写：多轮时把代词替换成具体概念，提升检索精度 |
| retrieve | RAG 检索：优先使用改写后的问题 |
| respond | 回答生成：带历史消息 + 分级 context 注入 + 忠实性约束 |

这里最反直觉的改动，是 `classify` 和 `refuse` 被移除了。

移除分类器不是一个计划内的决定。最初的设计是保留 classify，新拓扑长这样：

```text
START → summarize → classify → [rewrite → retrieve → respond | refuse] → END
```

但实现过程中发现，纯规则的分类器覆盖不了所有非数学输入。分类器要么太松（默认 textbook 导致乱答），要么太紧（误拒合法问题）。与其不断补充规则，不如把分类器去掉，改为在 respond 节点里做分级 context 注入——根据检索结果的相关性，决定给 LLM 多强的约束。

分类器的职责被两道防线替代了：

```text
第一道防线：respond 节点分级 context 注入
  检索结果高度相关 → 强约束："严格基于教材内容回答"
  检索结果相关性低 → 弱参考："可以参考，不相关基于知识回答"
  无检索结果 → 不注入 context

第二道防线：system prompt 忠实性约束
  最高优先级："绝不编造教材中没有的概念、定理、例题或比喻"
```

四个节点之间是线性传递。每个节点的输出写入 AgentState，下一个节点从 AgentState 读取输入。LangGraph 的 `checkpointer`（PostgresSaver）会在每个节点执行后自动持久化状态。

## 三、summarize：对话太长怎么办

summarize 要解决的问题是：对话越来越长，token 消耗越来越大，最终会超出 LLM 的 context window。

先定义了几个预算常量：

```text
CONTEXT_WINDOW       200,000    LLM context window 上限
SUMMARIZE_THRESHOLD  0.65       65% 时触发摘要 = 130K tokens
RESERVED_FOR_RAG     8,000      预留给 RAG context + system prompt
RESERVED_FOR_OUTPUT  4,000      预留给 LLM 输出
RECENT_MESSAGES_KEEP 10         摘要时保留最近 10 条消息（5 轮）
```

token 估算用的是粗略公式：`len(text) × 1.5`。中文字符大约占 1.5 个 token，精确计算可以用 tiktoken，但这里是粗略判断"是否超阈值"，不需要精确数字，粗估就够用了。

summarize 的执行逻辑：

```text
1. 估算当前对话总 token：已有摘要 + 所有消息 + 预留空间
2. 未超阈值（130K）→ return {}（什么都不做）
3. 超阈值 → 分割消息：保留最近 10 条，其余交给 LLM 生成摘要
4. 成功 → 返回摘要 + RemoveMessage 列表（清理被摘要的旧消息）
5. 失败 → return {}（什么都不做，下轮重新判断）
```

这里有几个设计细节。

**旧消息会被摘要替代。** 被摘要的旧消息不再参与后续回答，只保留合并后的摘要和最近几轮对话。这样既能控制上下文长度，也不会让用户感觉对话突然断掉。

**保留最近 10 条消息不参与摘要。** 这 10 条消息（大约 5 轮对话）直接透传给 respond 节点，保证近期的交互细节不会丢失。

**已有旧摘要时，新摘要会合并。** 旧摘要和新一批旧消息一起交给 LLM，生成合并后的摘要。这样摘要会越来越浓缩，而不是越来越长。

**summarize 失败不阻塞主流程。** LLM 调用超时或出错就跳过，下一轮用户提问时重新判断。token 超阈值是渐进问题，晚一轮摘要不会有严重后果。

前端只显示一条轻提示："上下文已压缩"，不打断用户继续提问。用户不需要知道后台压缩过上下文，但下一轮回答还能接住前文。

## 四、rewrite：把追问改成独立问题

rewrite 要解决的问题是：追问里的代词对 RAG 检索没有意义。

比如：

```text
第一轮："什么是函数？"      → 检索"什么是函数"，结果正确
第二轮："它的定义域怎么求？" → 检索"它的定义域怎么求"，结果跑偏
```

"它"指的是什么函数？向量检索模型不理解代词。

rewrite 的执行逻辑：

```text
1. 判断是否首轮：len(messages) <= 1 → return {}（不改写）
2. 多轮时，取最近 6 条历史消息，格式化为文本
3. 调用 LLM："基于对话历史，把追问改写为独立问题"
4. 成功 → 返回改写后的问题
5. 失败 → return {}（fallback 到原始 question）
```

改写后的效果：

```text
原始追问："它的定义域怎么求？"
改写结果："一次函数 y=2x+1 的定义域怎么求？"
```

retrieve 节点优先使用改写后的问题：

```text
query = state.get("rewritten_question") or state.get("question", "")
```

rewrite 没生效时（首轮或失败），就用原始问题。这个 fallback 是关键——rewrite 不是必须成功的，它是一个"尽量做得更好"的优化。

这里踩过一个小坑：如果 prompt 不明确要求"只输出问题"，LLM 很容易输出解释性前缀，比如"改写后的问题是：一次函数 y=2x+1 的定义域怎么求？"。后来在 prompt 里加了一句"直接输出改写后的问题，不要解释"，输出才稳定下来。

rewrite 生效时，前端只显示一条轻提示，比如"查询改写：一次函数 y=2x+1 的定义域怎么求？"。首轮不改写时不提示，用户无感。

## 五、respond 修复：历史消息终于传进去了

这一期最直接的 bug 修复就是 respond 节点。

之前 `_respond` 只传当前问题加 RAG 结果，不传历史。修复后的消息组装顺序：

```text
SystemMessage 1：教学策略 prompt + RAG context（分级注入）
SystemMessage 2（可选）：对话摘要
历史消息：summarize 清理后剩余的近期消息
→ 调用 LLM
```

这里重点说两个改动：分级 context 注入和忠实性约束。

### 分级 context 注入

之前 respond 是无条件注入检索结果的，并且带一句"请基于以上教材内容回答学生的问题"。这导致一个问题：检索结果和问题不相关时，LLM 仍然被指令强制基于检索内容回答，结果就是编造。

修复后，按检索结果的相关性分四级处理：

| 条件 | 注入策略 | prompt 约束 |
| --- | --- | --- |
| chunks 为空 | 不注入 context | 无特殊约束 |
| 高相关性（best_score >= 0.5） | 注入为"教材内容" | "严格基于教材内容回答，只使用明确出现的信息" |
| 低相关性（best_score < 0.5） | 注入为"参考内容" | "如果相关可参考，不相关基于知识回答并标注" |
| 降级（rerank 失败） | 注入为"参考内容" | 同上 |

相关性信号用的是 reranker 的分数。这是检索管线最后一道质量关卡，分数低于 0.5 说明检索结果大概率不匹配。

降级场景不使用相关性阈值，避免把不同来源的分数直接比较，误判检索质量。

### 忠实性约束

除了分级注入，还在 system prompt 最前面加了一段"忠实性约束"，标记为最高优先级：

```text
1. 只说教材中明确存在的内容
2. 绝不编造教材中没有的概念、定理、例题或比喻
3. 类比只能用于解释已有概念
4. 不确定时标注"教材中未直接涉及"
```

用"绝不"而不是"尽量避免"，是因为之前"尽量避免"措辞下 LLM 仍然会编造。零容忍的措辞遵从度更高。

这个约束和分级注入配合，形成了双层防护：分级注入决定"要不要用检索结果"，忠实性约束决定"用了以后能不能发挥"。

忠实性约束不是一开始就加的。最初只有分级注入，跑了一轮评估以后发现有些用例的 LLM 回答仍然不忠实——检索到了不相关内容，LLM 还是基于这些内容编造了回答。于是追加了 system prompt 的忠实性约束。这是评估驱动改进的一个实例。

## 六、这一期做完以后的变化

这一期做完以后，章鱼哥解题的多轮追问能力基本可用了。

学生问完"什么是函数"，再追问"它的定义域怎么求"，rewrite 会把代词替换成具体概念，retrieve 用改写后的问题检索，respond 带着历史消息回答。对话太长时，summarize 自动压缩，不会撞 context window。

分类器移除了，但分级 context 注入和忠实性约束替代了它的职责。不是靠规则判断"这算不算数学问题"，而是靠检索结果的相关性信号让 LLM 自己决定怎么回答。

这一期改动集中在后端，主要落在图拓扑、摘要/改写 prompt 和 token 预算几处。

也有几件事这一期没做。rewrite 的改写质量没有做改写前后的检索召回率对比。summarize 的压缩保真度没有覆盖更多场景。分级 context 注入的阈值 0.5 是经验值，没有做过敏感性分析。这些后面可以补。
