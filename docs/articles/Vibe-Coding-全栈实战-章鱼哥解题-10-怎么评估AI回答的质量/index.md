# Vibe Coding 全栈实战：章鱼哥解题 10｜给 AI 回答质量做一套回归测试

上一期改完了长对话管线：summarize 压缩、rewrite 改写、respond 历史消息修复、分级 context 注入。

改了这么多东西，怎么验证真的变好了？

AI 应用的质量问题很隐蔽。它不是每次都明显报错，而是可能在某个追问、某次话题切换、某轮长对话压缩后，悄悄丢信息、乱检索，甚至基于不相关内容编造回答。

手动试几个追问，看回答是否合理，这是一种方式。但手动测试有几个问题：不可重复（今天试和明天试结果可能不同）、不可量化（"感觉好一点"不是有效的判断）、不可回归（改了一个地方，另一个地方可能悄悄坏了）。

真正让我意识到这套评估必要性的，是一个看似无害的问题："今天天气怎么样？" 系统检索到了教材内容，却硬编出了一段教材解读。

所以这一期要搭一套评估体系。评估不是为了证明系统完美，而是为了发现它什么时候会悄悄变坏。具体来说，它要能回答这些问题：

```text
改写后的追问，检索结果是否真的变好了？
长对话压缩后，关键信息有没有丢失？
LLM 有没有基于不相关内容编造回答？
改了一个节点，其他节点有没有回归？
```

---

## 一、评估的整体结构

我的原则是：能用代码判定的，就不要交给 LLM；必须理解语义的，再交给 LLM Judge。

所以评估体系分两层：**确定性评估**和 **LLM-as-Judge 评估**。

```text
确定性评估（零成本，秒级完成）
  state_check        检查 AgentState 最终状态
  tool_calls         检查节点调用路径
  transcript         检查执行轨迹约束
  deterministic_filter  检查关键词和触发条件

LLM-as-Judge（有成本，分钟级完成）
  rewrite_quality    改写质量
  retrieval_relevance  检索相关性
  context_coherence  上下文连贯性
  summary_fidelity   摘要保真度
  grounding          接地性
```

确定性评估能快速发现回归问题，成本低、速度快，适合每次改代码后跑一遍。LLM-as-Judge 能覆盖确定性检查够不到的地方——改写语义是否完整、回答是否连贯、有没有编造。这两层配合使用，不是二选一。

---

## 二、评估数据集

所有评估都基于同一个数据集。人工标注了 46 条用例，覆盖 7 个层级。

这些用例不是为了凑数量，而是按"对话越长、指代越模糊、话题越容易跳"的方向逐级加难：

| 层级 | 用例数 | 测试场景 |
| --- | --- | --- |
| L1 | 8 | 简单代词替换、单轮无追问 |
| L2 | 9 | 省略补全、口语表达、话题切换 |
| L3 | 8 | 链式追问（3 轮）、追问后寒暄 |
| L4 | 7 | 显式话题切换、不应合并的话题 |
| L5 | 4 | 混合返回、跨主题引用 |
| L6 | 5 | 口语、复合问题、隐含追问、中断恢复 |
| L7 | 5 | 超纲问题（问候、天气、背诵古诗、做菜） |

32 条正面用例（期望走正常回答流程），14 条负面用例（期望拒答或弱回答）。

层级的设计思路是逐级增加难度：L1 只需要处理简单的代词替换，L3 要处理链式追问（3 轮），L5 要处理跨主题跳转后再返回，L7 是超纲问题专门测试接地性。

L7 的 5 条超纲问题是后来加的。最初数据集只有 L1-L6，跑完一轮评估以后发现 LLM 对超纲问题的回答仍然不忠实，于是追加了 L7。这个后面细说。

每条用例的定义格式：

```json
{
  "id": "L1-P01",
  "level": "L1",
  "category": "simple_pronoun",
  "negative": false,
  "turns": [
    {"role": "user", "content": "什么是函数？"},
    {"role": "user", "content": "它的定义域怎么求？"}
  ],
  "expected": {
    "rewrite_contains": ["函数", "定义域"],
    "intent": "textbook",
    "summary_triggered": false
  }
}
```

`expected` 字段定义了这条用例的期望行为：改写后应该包含哪些关键词、意图应该被分类为什么、summarize 是否应该被触发。确定性 grader 会逐项检查这些期望。

## 三、确定性评估

确定性评估不需要调用 LLM，成本为零，跑 46 条用例只需要几秒。

比如用户先问"什么是函数"，再追问"它的定义域怎么求"。如果 rewrite 后没有出现"函数"，这不需要 LLM 判断，直接失败；如果链路跳过 retrieve，也直接失败。

4 个 grader，各有侧重：

### state_check

检查 AgentState 的最终状态是否符合期望。

```text
首轮对话：
  rewritten_question 应为空（首轮不改写）
  conversation_summary 应为空（短对话不触发摘要）

多轮正面用例：
  rewritten_question 非空
  rewrite_contains 中的关键词全部出现

负面用例：
  不应该触发 retrieve 和 respond
```

这个 grader 能直接发现"rewrite 在首轮误触发"或"summarize 在短对话里误触发"这类问题。

### tool_calls

检查节点的实际调用路径。

```text
期望路径：summarize → rewrite → retrieve → respond
```

如果实际路径是 `summarize → rewrite → respond`（跳过了 retrieve），或者 `summarize → respond`（跳过了 rewrite），就说明某个节点的注册或边的连接出了问题。

### transcript

检查执行轨迹的约束。

```text
全链路耗时 <= 120 秒
```

如果某条用例耗时超过 120 秒，说明可能有卡点——LLM 调用超时、检索卡住、或者 summarize 的 LLM 调用没有正确 fallback。

### deterministic_filter

对正面和负面用例分别检查：

```text
正面用例：
  rewrite 后的问题包含 expected.rewrite_contains 中的关键词
  检索结果数量 >= 1

负面用例：
  rewrite 不应该包含特定内容
  不应该触发 retrieve 和 respond
```

这个 grader 是最粗的一层筛子，能快速发现改写跑偏、检索结果为空等问题。

### 为什么确定性评估要分 4 个 grader

一个 grader 检查所有东西也可以，但分开有好处：每个 grader 只关注一个维度，定位问题更快。如果 `state_check` 通过但 `deterministic_filter` 失败，问题大概率出在关键词匹配上，不是节点调用路径的问题。

## 四、LLM-as-Judge 评估

确定性评估能检查"结构是否正确"，但不能回答"改写后的语义对不对"、"回答有没有编造"这类需要理解内容的问题。

所以加了 LLM-as-Judge：用另一个 LLM 来评判 AI 回答的质量。

### 5 个评分维度

每个维度独立评分，0-5 分，外加 3 条断言（通过/不通过）：

| 维度 | 评估什么 | 适用范围 |
| --- | --- | --- |
| rewrite_quality | 改写后的问题是否语义完整、代词替换是否正确、能否独立理解 | 多轮正面用例 |
| retrieval_relevance | 检索结果是否和问题主题一致、是否包含关键术语 | 所有正面用例 |
| context_coherence | 回答是否引用历史概念、上下文是否连贯、教学语气是否一致 | 多轮正面用例 |
| summary_fidelity | 摘要是否覆盖了原始对话的主要话题、因果链是否保留 | summarize 触发时 |
| grounding | 回答是否忠于教材、有没有编造 | 超纲用例 |

评分标准统一：

```text
5 = 完美
4 = 良好
3 = 可接受
2 = 较差
1 = 完全错误
0 = Unknown（信息不足，无法判断）
```

### Judge prompt 的设计

每个维度的 Judge prompt 都包含三个部分：

```text
1. 评分标准（rubric）：0-5 分各自的定义
2. 断言检查（assertions）：3 条具体的通过/不通过检查
3. 输入数据：对话历史、改写结果、检索结果、AI 回答等
```

断言检查比分数更有用。分数是主观的，不同 Judge 可能给不同分数；但断言是客观的——"改写后是否包含原始问题中的数学概念"只有通过和不通过。

以 `rewrite_quality` 为例，3 条断言是：

```text
1. 改写后包含原始问题中的数学概念
2. 代词已被替换为具体概念
3. 改写后可独立理解，无需对话上下文
```

### Judge 输出格式

要求 Judge 输出严格的 JSON：

```json
{
  "score": 4,
  "assertions": [true, true, false],
  "reasoning": "改写后正确将'它'替换为'函数'，但末尾多了一句解释"
}
```

`score = 0` 被标记为 Unknown——Judge 认为信息不足以判断。这不是"最差"的意思，而是"无法评估"。如果 Judge 返回 `score = 0`，这条评分会被排除，不计入平均分。

### 综合判定规则

确定性评估和 LLM-as-Judge 不是独立评判，而是组合判定：

```text
确定性全部通过 + LLM 平均分 >= 3.5 + 断言通过率 >= 70% → PASS
确定性全部通过但 LLM 未达标 → CONDITIONAL_PASS
确定性有失败 → FAIL
```

确定性失败直接 FAIL，不看 LLM 分数。因为如果节点调用路径都不对，LLM 打多少分都没有意义。

## 五、一个天气问题暴露了 grounding 漏洞

grounding 维度不是一开始就有的，它是评估过程中发现的遗漏。

最初评估只覆盖了 4 个维度：rewrite_quality、retrieval_relevance、context_coherence、summary_fidelity。跑完一轮以后，发现 L1-L4 的正面用例得分都不错，但有一些用例的 LLM 回答仍然不忠实——检索到了不相关内容，LLM 还是基于这些内容编造了回答。

比如有一条测试用例问"今天天气怎么样"，系统检索到了一些教材内容（因为 classify 默认返回 textbook），LLM 被指令强制基于检索内容回答，结果编造了一段和天气无关的教材解读。它没有说"教材未涉及天气"，而是硬把天气问题解释成数学教材内容。

这说明两个问题：

1. 评估数据集缺少"超纲问题"的用例（于是追加了 L7 的 5 条）
2. 缺少"接地性"的评分维度（于是新增了 grounding 维度和 GROUNDING_PROMPT）

grounding 维度的 3 条断言：

```text
1. 回答只使用了检索内容中明确出现的信息
2. 回答没有编造检索内容中不存在的概念或例题
3. 对不确定的内容标注了"教材中未直接涉及"
```

这个维度加进去以后，不仅评估体系更完整了，还推动了上一期 system prompt 的忠实性约束——评估发现了问题，才回来补了约束。这就是评估驱动改进的实例：不是先设计完美再评估，而是评估发现漏洞再补。

## 六、专项测试：50 轮超长对话

除了 46 条主数据集，还做了一个专项测试来验证 summarize 节点。

构建了一个覆盖高中数学多个主题的长对话，50 轮，每轮要求 LLM 生成 800 字以上的回答。目的是让 token 消耗超过 130K 的阈值（200K × 65%），确保 summarize 节点真的会被触发。

为什么需要专项测试？因为 46 条数据集中的用例轮数都比较短（1-3 轮），token 消耗远低于 130K，summarize 不会触发。summarize 的触发条件是"长对话"，需要刻意构造长对话才能测到。

测试验证了两件事：

1. **触发确认**：token 估算超过阈值后，summarize 节点确实被触发，生成了摘要并清理了旧消息
2. **摘要保真度**：通过 LLM Judge 的 `summary_fidelity` 维度评估，摘要确实覆盖了原始对话的主要话题，因果链保留完整

通过标准：`summary_fidelity` 得分 >= 3 且至少 2 条断言通过。

---

## 七、评估结果

最终跑出来的结果是：

- 确定性评估：46/46 全部通过
- LLM-as-Judge：5 个维度平均分均 >= 3.5，断言通过率 >= 70%
- 专项测试：50 轮超长对话 summarize 触发成功，摘要保真度达标

这组结果的意义不是"AI 回答已经完美"，而是说明这次长对话改造没有只在几个手工 demo 里变好：追问改写、检索相关性、上下文连贯性、摘要保真度和接地性都能被重复检查。

代码实现集中在 `backend/eval/` 下，包括数据集、确定性 grader、LLM Judge prompt 和长对话专项测试。

## 八、这套评估体系以后怎么用

这套评估体系不只是用来验收上一期的改动，它是一个可持续使用的基础设施。

后续每次改 prompt、改检索策略、加新节点，都可以用同一套数据集跑分，对比前后变化。确定性评估秒级完成，适合每次提交后跑；LLM-as-Judge 分钟级完成，适合阶段性验证。

也有几件事这一期没做。数据集只有 46 条，覆盖场景有限。LLM Judge 用的是同一个模型（glm-5.1），存在"自己评自己"的偏差风险。评估报告目前是终端输出，没有持久化到数据库。这些后面可以补。
