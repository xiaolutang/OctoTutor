# 写作风格指南

> 所有项目技术文章遵循以下风格规范，保持语气统一。

## 核心原则

**探索实战，不是说教。** 记录的是"我做了什么、踩了什么坑、怎么解决的"，而不是"你应该这样做"。

## 语气对照

### 开头：用具体数据或场景切入，不用宏大宣告

```
✓ 高峰期每天消耗约 6 亿 token——这是我现在用 AI 写代码的日常。
✓ 上个月我让 AI 帮我接 OAuth 登录，它写得很快，但上线后回调被触发了两次。

✗ 最近半年，我的开发方式发生了根本性的变化。
✗ 在 AI 辅助编码的时代，开发者真正需要掌握的是什么。
✗ 作为一名开发者，我一直在思考……
```

### 发现问题：用"发现了一个有意思的事情"，不用"我们不得不承认"

```
✓ 用着用着，我发现了一个有意思的事情：AI 生成的单个模块通常没问题，但拼在一起时总会冒出缝隙。
✓ 这时候遇到了一个问题：回调被触发了两次。

✗ Vibe Coding 可以生成代码，但不能替代架构思考。
✗ 我们不得不承认，AI 还无法替代人类的架构决策能力。
```

### 动机：用"所以我萌生了一个想法"，不用"这正是我的核心动机"

```
✓ 所以我萌生了一个想法：从零搭一个完整的全栈应用，看看哪些环节 AI 能搞定，哪些必须自己来。
✓ 我想试试从零开始搭，把整条链路自己走一遍。

✗ 这正是我做这个项目的核心动机：通过从零搭建一个完整的全栈应用，验证……
✗ 我决定通过这个项目来系统性探索全栈开发的最佳实践。
```

### 解决方案：展示过程，不只给结论

```
✓ 我考虑过三种方式：A 方案……B 方案……最终选了 C，因为……
✓ 最初的实现是 config.json 静态文件，但每次发布都要改，后来换成了……

✗ 经过深思熟虑，我采用了最优方案。
✗ 显而易见，运行时配置注入是更好的选择。
```

### 踩坑记录：讲清楚"坑是什么"和"为什么会有这个坑"

```
✓ React 18 的 StrictMode 会在开发模式下双重渲染组件，导致 handleCallback() 被调用两次。
✓ OAuth 登录涉及页面跳转，回来后 React 组件树重建，之前的路由状态丢失。

✗ 这里有个 bug，用 useRef 修一下就好了。
✗ 遇到了一个常见问题，解决方案如下。
```

### 总结：复盘语气，不做升华

```
✓ 回头看这一阶段，踩了不少坑，但也有几个决策做对了：
✓ 不过这些都是基础设施，章鱼哥现在还不会解题。

✗ 通过本项目，我们深刻认识到全栈开发需要掌握以下四大能力：……
✗ 展望未来，AI 辅助开发必将改变软件工程的方方面面。
```

## 禁用句式

| 类型 | 示例 | 替代写法 |
|------|------|----------|
| 宣告式开头 | "XX正在改变世界" | 用具体数据或故事开头 |
| 说教式结论 | "开发者应该掌握的是……" | "我发现的是……" |
| 伪升华 | "这不仅是一次技术实践，更是……" | 删掉，或者换成具体的下一步计划 |
| 简历式自我介绍 | "作为一名XX，我具有XX经验" | 不需要背景铺垫，直接进入正题 |
| 标题党小标题 | "环境隔离的秘密" | "环境隔离的实现方式" |
| 口号 | "一次构建，到处运行" | 描述实际效果 |

## 保留的元素

- 具体数据（53MB 镜像、6 亿 token、300 粒子）
- 代码片段（关键方案保留核心代码，不贴全量）
- 方案对比表格（让读者自己判断）
- 踩坑的根因分析（不只说"怎么修"，还要说"为什么会有这个问题"）
- 章节间的过渡句（让文章读起来连贯，不像拼凑的）

## 技术文章的事实边界

写项目复盘文章时，不能只靠记忆或当前代码推断。每篇文章都要尽量对齐对应阶段的四类材料：

- 需求分析：这一期到底要解决什么问题，哪些事情明确不做。
- 方案设计：为什么这样拆模块，为什么选这个方案，不选哪些方案。
- 实际代码：最终实现是不是和文章描述一致，尤其是调用方向、异常分支和边界行为。
- 验收证据：哪些场景真的测过，哪些只是设计考虑或后续可补。

写作时要区分三种表达：

| 类型 | 可以怎么写 | 避免怎么写 |
| --- | --- | --- |
| 已实现且已验证 | "单元测试覆盖了三个并发请求同时 401，只刷新一次" | "这个方案完全解决了并发安全问题" |
| 已实现但未专门测试 | "当前实现依赖 TokenManager 返回 null 进入会话过期流程" | "已经保证用户退出时不会恢复旧会话" |
| 设计目标或后续方向 | "后面可以在 AuthContext 加 redirecting 标记" | "系统已经避免重复跳转登录" |

如果文章里用了"保证"、"一定"、"不会"、"统一"这类词，要反查实际代码和测试证据。没有证据时，改成"当前设计会"、"这一期先"、"后续可以补强"。

## 代码和图的写法

- 代码片段只保留关键逻辑，但不能删掉会改变行为理解的分支。
- 如果代码是简化版，要明确写"简化后大概是这样"。
- 图里的箭头要表达真实关系：函数调用、注册关系、HTTP 请求、数据返回不要混成一种箭头。
- 前端到后端的调用建议用虚线，表示跨网络请求；模块内部调用用实线。
- 图只画当前文章主线，不要为了完整性把无关模块都放进去。

## 发布前验收维度

每篇文章发布前至少从这些维度过一遍：

| 维度 | 要看什么 |
| --- | --- |
| 结构连贯性 | 前言、问题、方案、实现、验收、总结是否顺着一条主线走；章节有没有重复或强行插入 |
| 事实准确性 | 是否基于对应阶段的需求分析、方案设计、实际代码和验收证据；有没有拿当前新代码反推旧文章 |
| 边界清晰度 | 哪些做了、哪些没做、哪些只是后续方向；有没有过度承诺 |
| 代码一致性 | 代码片段是否和实际实现一致；简化片段是否会误导读者 |
| 图表准确性 | 流程图、时序图、模块图的方向和关系是否真实；前后端、注册、调用、HTTP 是否区分清楚 |
| 验收可信度 | 测试、抽检、评估是否说明了验证什么；没有测过的场景不要写成已验证 |
| 读者可理解性 | 名词第一次出现是否解释；内部需求编号不要直接丢给读者 |
| 发布清洁度 | 没有 TODO、"当时"滥用、"我觉得"、内部讨论痕迹、失效章节编号、不可见图片路径 |

审稿时优先找问题，不先润色。顺序建议是：

1. 先看主线是否成立。
2. 再看事实和代码是否对得上。
3. 再看边界有没有说过头。
4. 最后才处理句子顺不顺、标题好不好。
